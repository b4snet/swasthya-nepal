# Swasthya — Supabase PostgreSQL Staging Runbook

> **Status:** CONFIGURATION READY — not deployed. This runbook records the
> decision to use **Supabase managed PostgreSQL** as the staging database for
> the Laravel API and the exact steps to do it safely. **No deployment has
> happened** and no Supabase credentials are committed anywhere; every value
> below is a placeholder to be entered in the Render environment at creation
> time.

---

## 1. Why this works — compatibility verdict

Swasthya's database architecture (PostgreSQL, migrations, least-privilege
`swasthya_app` role, RLS policies, tenant GUCs) is **compatible** with
Supabase managed PostgreSQL, with **one hard constraint** (session pooler,
§2). Verified against Supabase's own documentation:

| Swasthya requirement | Supabase capability | Verdict |
|---|---|---|
| PostgreSQL 16+ | The project (`bgfqwsivvhqmuwullkye`) actually runs **PostgreSQL 17.6**; the migrations are verified on both 16 (CI/disposable) and 17.6 (live) | ✅ |
| Custom application role (`swasthya_app LOGIN … NOBYPASSRLS`) | `create role "x" with login password '…'` is documented; the `postgres` role has admin privileges and can create roles | ✅ |
| `roles.sql` / `grants.sql` (GRANT … / ALTER DEFAULT PRIVILEGES) | Standard SQL, runnable as `postgres` | ✅ |
| RLS: `ALTER TABLE … ENABLE ROW LEVEL SECURITY` + `CREATE POLICY` | Standard SQL; policies apply to the non-superuser `swasthya_app` (NOBYPASSRLS) exactly as designed | ✅ |
| Tenant GUCs (`set_config('app.*', …, is_local)`) | Session-level custom GUCs are settable by any role; transaction-local scoping is safest | ✅ |
| `pg_trgm` extension (patient search) | Pre-installed / installable on Supabase | ✅ |
| Migrations + `migrate --force` as owner | Owner = `postgres` (bypasses RLS during DDL, like the local owner `swasthya`) | ✅ |
| TLS | Supabase requires SSL for external connections; `DB_SSLMODE=require` | ✅ |
| IPv4 | Shared pooler is **IPv4-only on every tier** — correct for Render | ✅ |
| Backups / PITR | Supabase paid plans: automatic daily backups + PITR (7 days) | ✅ (paid plan; billing decision) |
| No `migrate:fresh` / `DROP DATABASE` / destructive resets | Never part of the bootstrap (§4) | ✅ |

**What is intentionally NOT used:** Supabase's JS client, Supabase Auth,
PostgREST, and the `anon`/`authenticated`/`service_role` roles. Laravel
authenticates with its own Sanctum tokens; the API connects only as
`swasthya_app`. The `auth`/`storage` schemas Supabase creates are never
touched; all Swasthya tables live in `public`.

## 2. Connection architecture — the one hard constraint

**Use the shared pooler in SESSION mode (port 5432), never transaction mode
(6543).**

- **Session mode** pins each client connection to one backend, so Laravel's
  per-connection `SET search_path` / `SET time zone` and PDO server-side
  **prepared statements** work. This is the documented choice for
  "persistent backend on IPv4-only networks" — exactly Render.
- **Transaction mode** (6543) does **not support prepared statements** and
  does not persist session-level SET — Eloquent would fail intermittently.
- **Direct connection** (`db.<ref>.supabase.co`) is **IPv6-only** unless the
  IPv4 add-on is purchased — unusable from Render without the add-on.

The pooler username carries the project reference: `<role>.<project-ref>` —
e.g. `swasthya_app.bgfqwsivvhqmuwullkye` and `postgres.bgfqwsivvhqmuwullkye`.
Copy the session-pooler connection string from Dashboard → Connect and split
it into `DB_HOST` / `DB_USERNAME` / `DB_PASSWORD`.

## 4. First-time database initialization (safe, non-destructive)

The Render **predeploy command** runs this automatically and **aborts the
deploy on any failure** (`set -e`, `ON_ERROR_STOP`, `preDeployCommand`
semantics). It never runs `migrate:fresh`, `db:wipe`, or `DROP DATABASE`:

1. **`database/security/roles.sql`** — creates `swasthya_app` with
   `NOBYPASSRLS` and the exact password stored in `DB_PASSWORD`
   (idempotent; a no-op if the role already exists). Runs as `postgres`.
2. **`php artisan migrate --force`** — applies only forward migrations as the
   owner. The RLS migration (`enable_row_level_security`) asserts
   `swasthya_app` exists, enables RLS, creates the tenant policies, and
   grants DML + default privileges to `swasthya_app`.
3. **`database/security/grants.sql`** — idempotent re-application of grants
   (covers restores, where `ALTER DEFAULT PRIVILEGES` is not preserved by
   `pg_dump`).

**Manual alternative (Path B)** — if you prefer to create the role in the
Supabase SQL Editor before the first deploy instead of letting the predeploy
do it, run this once as `postgres` (replace the password with the same value
you will store in `DB_PASSWORD`):

```sql
-- Supabase SQL Editor (runs as postgres). Optional — the predeploy
-- bootstrap (roles.sql) does the same thing and is idempotent.
select format(
    'create role swasthya_app login password %L nosuperuser nocreatedb nocreaterole noinherit noreplication nobypassrls',
    '<DB_PASSWORD>'
)
where not exists (select from pg_roles where rolname = 'swasthya_app')
\gexec
```

Do **not** grant `swasthya_app` table ownership, `BYPASSRLS`, or DDL. The RLS
migration creates the tables' grants; `grants.sql` is the post-restore fixup.

### Rollback / correction

To rotate the runtime password later, run as `postgres`:

```sql
alter role swasthya_app with password '<new-password>';
```

and update `DB_PASSWORD` in Render to the same value.

## 5. RLS and tenant isolation on Supabase

- The 144 RLS policies created by the migrations apply to `swasthya_app`
  exactly as they do locally and in CI (CI proves them against a disposable
  `postgres:16` on every run — including cross-tenant, cross-facility,
  cross-branch, audit-append-only, and support-session tests).
- `postgres` (the owner) bypasses RLS during migrations/seeds — identical to
  the local owner design. **Runtime traffic never uses `postgres`.**
- Supabase's own `anon`/`authenticated`/`service_role` roles and the
  `auth`/`storage` schemas are unrelated and untouched. The Supabase Table
  Editor (dashboard) connects with elevated admin access, which is expected
  operator access — not application access.

## 6. Backups and restore on Supabase

- Supabase paid plans provide **automatic daily backups + point-in-time
  recovery (7 days)** and logical exports — this satisfies the
  DISASTER_RECOVERY.md requirement that Render-managed Postgres would have.
  Free projects have no backups; confirm the paid plan as part of the billing
  decision.
- **Restore into a fresh project / database** must re-create cluster-level
  state that `pg_dump` does not carry:
  1. `database/security/roles.sql` (recreates `swasthya_app`).
  2. Restore the dump (schema + data).
  3. `database/security/grants.sql` (re-applies DML + default privileges).
  - The RLS policies and the audit hash-chain are schema objects and restore
    with the dump; the tenant GUC mechanism is application-side.

## 7. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `prepared statement ... already exists` or intermittent 57P01 under load | You are on **transaction mode (6543)** — use session mode (5432). |
| `Connection refused` | Pooler client limit reached (small on free tier; `pm.max_children=8` in the image is well within it). |
| `FATAL: password authentication failed` | `DB_PASSWORD` ≠ the password `swasthya_app` was created with (roles.sql uses `DB_PASSWORD` as the single source of truth). |
| `role "swasthya_app" does not exist` at deploy | Predeploy bootstrap failed before `roles.sql`; read the Render deploy log — it is fail-closed. |
| Search queries fail | `pg_trgm` must be created — the `create_patients_table` migration does `create extension if not exists pg_trgm` during `migrate --force`. |

## 8. Explicitly NOT done (and not claimed)

- **No deployment** — nothing has been provisioned or deployed.
- **No Supabase credentials in git** — credentials live only in the
  gitignored `backend/.env.supabase` and Render's environment.
- **No migration of existing data** — the Supabase `public` schema was

- **No weakening of the security model** — RLS, `swasthya_app`

## 9. Live bootstrap results (2026-08-12)

The first real connection to the project surfaced two host-dependent defects
that the disposable-Postgres CI could not see. Both were fixed in the
`enable_row_level_security` migration and re-applied to the live database.

**Finding 1 — owner-role resolution.** `grantApplicationPrivileges()` derived
the owner from `DB::connection()->getConfig('username')`. Through the pooler
that string is the alias `postgres.bgfqwsivvhqmuwullkye`, which is not a role
that exists server-side, so `ALTER DEFAULT PRIVILEGES FOR ROLE "postgres.bg…"`
failed and the RLS migration rolled back. Fix: resolve the owner from
`select current_user` (the real session role) — correct on every host.

**Finding 2 — Supabase enables RLS on new tables by default.** This project's
"Enable RLS on new tables" setting (Dashboard → Authentication → Policies) is
on, so every table the migrations created — including the identity/root/
framework tables that the architecture deliberately leaves **not** RLS-scoped
(organizations, users, roles, permissions, role_permissions,
personal_access_tokens, refresh_tokens, cache, jobs, …) — got RLS enabled
with **zero policies**, silently blocking the application role (login reads
`users`, Sanctum reads `personal_access_tokens`, queue/cache read framework
tables). Fix: the RLS migration now **enforces the documented matrix on any
host** — RLS stays on only for the scoped tenant-owned tables; every other
public table is explicitly `DISABLE ROW LEVEL SECURITY` (idempotent).
`down()` also gained the missing `facilities` entry.

**Verified against the live Supabase database (all non-destructive):**
- `roles.sql` created `swasthya_app` — `rolsuper=f`, `rolbypassrls=f`,
  `rolcanlogin=t`, `rolcreaterole=f`, `rolcreatedb=f`, `rolreplication=f`.
- `php artisan migrate --force` applied all **47 migrations** (Postgres 17.6).
- **144 RLS policies** present; RLS on for all tenant tables, off for the
  identity/root/framework tables.
- `swasthya_app` connected through the session pooler (runtime path).
- Live cross-tenant probe as `swasthya_app` inside a rolled-back transaction:
  Tenant A insert + read → **1 row**; Tenant B read → **0**; Tenant B update →
  **0 rows**; after rollback → **0 rows persisted**.
- Full backend suite on disposable PostgreSQL 16: **241 passed / 1,748
  assertions**; RLS/isolation suites: **47 passed / 133 assertions**.

These two migration fixes are in the working tree (uncommitted); a fresh CI
run will re-prove them against disposable PostgreSQL.
